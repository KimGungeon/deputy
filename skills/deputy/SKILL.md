# deputy 프로토콜

여러 Claude Code 세션이 사람 없이 협업한다. 상태는 전부 GitHub 이슈에 있고,
로컬에 숨은 저장소는 없다. 사람은 출근해 있으며 폰으로 이슈를 본다.

## 두 가지 역할

| 역할 | 담당 디렉터리 | 하는 일 |
|---|---|---|
| **담당자** (builder) | 있음 | 제안하고, 합의되면 구현하고, 완료 처리한다 |
| **조율자** (coordinator) | **없음** | 구현하지 않는다. 리뷰·중재·백로그 관리만 한다 |

조율자가 필요한 이유는 담당자가 자기 영역만 보기 때문이다. 두 제안이 같은 파일을
건드리는지, 순서가 뒤집혔는지, 어떤 작업이 멈춰 있는지는 **전체를 보는 눈이 있어야**
보인다. 조율자는 담당 디렉터리가 없으므로 파일 충돌을 일으킬 수 없고, 담당자가
둘뿐일 때 실질적인 정족수를 만들어 준다.

조율자는 `deputy claim` 이 거부된다. 코드를 고쳐야 하면 담당 세션에 요청한다.

## 이슈 하나를 지목할 때

```
deputy <이슈번호>
```

상태를 읽어 다음 행동을 판단하고, 인자가 필요 없는 것은 바로 실행한다.
12개 명령을 외울 필요 없이 번호만 주면 된다. 매 턴의 시작은 여전히 `deputy next` 다.

## 매 턴의 시작

```
deputy next
```

**무엇을 할지는 이 출력이 정한다.** 스스로 정하지 않는다.
출력은 이미 우선순위대로 정렬되어 있다:

| 순위 | 내용 | 왜 이 순서인가 |
|---|---|---|
| 0 | 사람이 남긴 코멘트 | 유일한 외부 신호다. 무엇보다 먼저 반영한다 |
| 1 | 내가 해야 할 리뷰 | 내가 안 하면 남이 막힌다 |
| 2 | 내가 진행 중인 작업 | 벌여놓고 안 끝내는 게 가장 나쁘다 |
| 3 | 내 제안의 판정 | 합의됐으면 착수, 이견이 있으면 수정 |
| 4 | 새 작업 제안 | 위가 전부 비었을 때만 |

## 제안하기

```
deputy propose <이슈번호> \
  --why "왜 지금 이것인가" \
  --alternatives "다른 후보를 왜 뒤로 미뤘는가" \
  --done-when "무엇이 참이면 끝인가 - 명령과 기대 출력으로" \
  --files "src/api/**" --estimate "1h"
```

- **`--why` 없이 제안하지 않는다.** "백로그에 있어서"는 근거가 아니다.
  지금 이걸 먼저 해야 하는 이유, 이게 풀어주는 다음 작업, 미뤘을 때의 비용을 쓴다.
- **`--alternatives` 를 비워두지 않는다.** 대안을 비교하지 않은 제안은 리뷰에서 막힌다.
- **`--done-when` 은 검증 가능해야 한다.** "코드가 깔끔해진다"는 안 된다.
  "`pytest -q tests/api` 가 0으로 끝난다"는 된다.

## 리뷰하기

```
deputy review <이슈번호> --verdict AGREE|OBJECT|AMEND --reason "..."
```

**형식적으로 AGREE 만 찍지 않는다.** 그러면 합의 절차 전체가 의미를 잃는다.
리뷰 전에 반드시:

1. 제안이 건드린다는 파일을 실제로 읽는다
2. 제안자가 놓친 의존 관계나 부작용을 찾는다
3. 완료 기준이 정말 검증 가능한지 확인한다

그런 다음 판단한다:

- **AGREE** — 근거가 타당하고 완료 기준이 검증 가능하다. 무엇을 확인했는지 쓴다
- **AMEND** — 방향은 맞지만 범위나 순서를 고쳐야 한다. 무엇을 어떻게 고칠지 쓴다
- **OBJECT** — 지금 하면 안 된다. 왜 안 되는지와 대신 무엇을 해야 하는지 쓴다

내 담당 영역과 충돌하는 제안은 반드시 지적한다. 그게 내가 리뷰하는 주된 이유다.

## 합의와 진행

```
deputy consensus <이슈번호>     # 판정 확인
deputy claim <이슈번호>          # 합의됐으면 착수
deputy done <이슈번호> --close --result "무엇을 했고 어떻게 검증했는지"
```

판정은 결정론적이며 **절대 교착하지 않는다**:

- `CLAIM` — 착수해도 된다
- `REVISE` — 이견이 있다. 리뷰를 읽고 `deputy propose` 로 수정본을 올린다
- `ESCALATE` — 수정 한도를 넘겼다. 이견이 가장 적은 범위로 좁혀 진행하고 근거를 남긴다
- `WAIT` — 리뷰 대기 중. **여기서 멈추지 않는다.** 제한 시간이 지나면 기권 처리되어
  자동으로 진행된다. 기다리는 동안 사전 조사를 한다

## 큰 이슈를 만났을 때 — 분해

이슈가 한 번에 끝낼 수 없을 만큼 크면 구현하지 말고 **쪼갠다.**
큰 이슈를 그대로 붙잡으면 컨텍스트가 넘쳐 목표가 해제되고 세션이 멈춘다.

```
deputy plan --template            형식과 규칙을 본다
deputy plan 7 --file plan.json    분해안을 제출한다
deputy plan 7 --apply             합의된 뒤 실제 이슈로 만든다
```

### 분해는 합의를 거친다 (파생 이슈와 다른 점)

| | 파생 이슈 | 분해 |
|---|---|---|
| 성격 | 이미 합의된 완료 기준이 **강제하는 사실** | 여러 갈래 중 **하나를 고르는 선택** |
| 합의 | 거치지 않음 | **거친다** |
| 틀렸을 때 | 작업 하나가 늘어남 | 8시간이 통째로 날아감 |

### 분해안이 통과해야 하는 검사

`deputy plan` 이 자동으로 막는다. 건너뛸 수 없다.

- `owner` 는 **담당자**여야 한다. 조율자는 구현하지 않으므로 담당이 될 수 없다
- 담당이 한 명으로 몰리면 거부된다. 병렬로 돌릴 이유가 없어지기 때문이다
- `done_when` 은 **실행할 명령과 기대 결과**로 쓴다. "잘 동작한다"는 거부된다
- `after` 에 순환이 있으면 거부된다. 선행이 없는 자식이 최소 하나 있어야 한다
- 자식은 최대 12개. 넘으면 에픽 자체가 너무 크다는 뜻이니 에픽을 나눈다

### 분해할 때 생각할 것

- **인터페이스를 고정하는 작업을 먼저 둔다.** 그래야 나머지가 병렬로 갈 수 있다
- **담당이 갈리게 자른다.** 두 자식이 같은 파일을 건드리면 분해가 잘못된 것이다
- **사람 없이 검증 가능하게 자른다.** 소리를 듣거나 화면을 봐야 확인되는 완료 기준은
  무인 운영에서 검증할 수 없다. 픽스처 기반 테스트로 바꿔 쓴다
- 새 디렉터리를 만드는 작업이면 **뼈대를 만드는 자식을 첫 번째로** 둔다.
  아무도 담당하지 않는 디렉터리에 두 세션이 각자 구조를 만들면 충돌한다

### 적용 후

자식 이슈는 승인된 계획에서 나왔으므로 **재합의 없이 바로 착수**한다.
`deputy next` 가 담당자에게 배정된 자식을 알려주고, 선행 작업이 안 끝난 것은
자동으로 걸러준다. 에픽은 자식이 모두 닫히기 전에는 닫히지 않는다.

## 작업 중 문제를 발견했을 때

작업하다 다른 문제를 발견하는 건 정상이다. 문제는 그걸 **어디에 담느냐**다.
아래 세 질문을 순서대로 던지고, 처음 걸리는 데서 멈춘다.

1. **이걸 안 고쳐도 부모 이슈의 완료 기준(`done-when`)이 통과하는가?**
   → 통과한다면 **파생 이슈가 아니다.** 독립된 새 이슈(`gh issue create`)로 만들거나,
     티켓을 만들 만큼도 아니면 `deputy note` 로 남긴다.
2. **이걸 안 고친 채로 부모를 닫아도 안전한가?**
   (회귀를 만들지 않고, 깨진 상태를 남기지 않고, 리뷰어가 동의한 내용과 어긋나지 않는가)
   → 안전하다면 역시 **파생 이슈가 아니다.**
3. 둘 다 **아니오** — 이걸 고치지 않으면 부모의 완료 기준을 정직하게 만족시킬 수 없다
   → **파생 이슈다.**

```
deputy derive <부모번호> --why "무엇을 발견했고 왜 부모가 이것 없이는 끝날 수 없는지" \
                       --done-when "무엇이 참이면 이 파생 작업이 끝인가"
```

### 판단 예시

| 상황 | 판정 |
|---|---|
| 레이트 리밋 구현 중, 설정 로더가 잘못된 YAML 을 조용히 삼키는 걸 발견 | **파생** — 설정이 깨지면 "임계값대로 제한된다"를 검증할 수 없다 |
| 같은 작업 중, 설정 핫리로드가 없는 걸 발견 | **독립 이슈** — 핫리로드 없이도 레이트 리밋은 정상 동작한다 |
| 깨지는 테스트 수정 중, 원인이 12개 테스트가 공유하는 전역 타이머임을 발견 | **파생** — 단, `setup.py` 의 타이머 경합만. 나머지 11개 점검은 독립 이슈 |
| API 엔드포인트 추가 중, 옆 함수 docstring 오타 발견 | **노트** — 티켓도 아니다 |
| 컬럼 마이그레이션 중, 다른 테이블에도 같은 문제가 있는 걸 발견 | **독립 이슈** — 부모의 완료 기준은 A 컬럼에 대한 것이다 |

### 상한 — 반드시 지킨다

- **깊이 1단계.** 파생 이슈는 자식을 가질 수 없다. 파생 작업 중 발견한 문제는
  노트이거나 독립 이슈다. 이 규칙이 무한 증식을 막는다
- **부모당 파생 3개.** 네 번째가 나온다면 그건 파생이 더 있다는 뜻이 아니라
  **부모의 범위 설정이 틀렸다는 신호다.** 더 만들지 말고 부모에 코멘트로
  "범위가 잘못 잡혔다, 이렇게 쪼개야 한다"를 남기고 다음 작업으로 넘어간다.
  사람이 아침에 읽고 다시 자른다
- **크기 제한.** 파생 이슈는 부모보다 작아야 한다. 부모보다 크면 그건 파생이 아니라
  여기서 발견됐을 뿐인 독립 작업이다

### 파생 이슈는 합의를 거치지 않는다

파생 이슈에는 propose → review → consensus 를 적용하지 않는다. 합의 절차는
**무엇을 할지 고르는 판단**을 검증하기 위한 것인데, 파생 이슈는 선택이 아니라
이미 합의된 부모의 완료 기준이 강제하는 사실이기 때문이다. 여기에 45분 리뷰
타임아웃을 걸면 자기 자식을 기다리다 멈추는 교착만 만든다.

대신 **부모 이슈에 반드시 보이게 남긴다.** `deputy derive` 가 부모 본문의 체크리스트에
`- [ ] #<자식번호>` 를 추가하므로 다른 세션과 사람이 즉시 본다. 다른 세션이
"이건 범위 확장이다"라고 판단하면 사후에 이의를 제기할 수 있다.

### 부모는 자식이 다 닫히기 전에 닫히지 않는다

`deputy done <부모> --close` 는 열린 파생 이슈가 있으면 닫기를 거부한다.
**여기서 멈추지 않는다.** 거부 메시지를 읽고 `deputy next` 를 실행하면
다음에 처리할 파생 이슈를 알려준다. 부모와 파생을 모두 끝낸 뒤에야
다음 최상위 작업으로 넘어간다.

## 기다릴 때 하는 일

`WAIT` 는 쉬라는 뜻이 아니다. 합의 직후 바로 구현에 들어갈 수 있게 준비한다:

- 관련 코드를 읽고 현재 동작을 파악한다
- 재현 케이스나 실패하는 테스트를 먼저 써둔다
- 알아낸 것을 `deputy note <번호> "..."` 로 이슈에 남긴다

## 다른 세션에게 알리기

판정이 나오거나 작업을 끝냈으면 해당 세션에 직접 알린다:

```
@beta 이슈 #12 리뷰 부탁해. 네 담당인 src/db 에 영향이 있어.
@alpha #12 리뷰했어. AMEND — 마이그레이션 순서를 뒤집어야 해.
```

이슈 코멘트로도 남지만, 메시지를 보내야 상대가 즉시 움직인다.

## 절대 하지 않는 것

- 담당 밖 파일 수정 — 다른 세션과 충돌한다
- `main`/`master` 로 push
- 배포, DB 마이그레이션 실행, 시크릿 조작
- 이견이 남았는데 `deputy claim --force` 로 밀어붙이기
- 근거 없이 AGREE 를 찍어 합의를 통과시키기
- 조율자가 코드 파일을 직접 수정하기
- 파생 이슈에 또 파생 이슈 만들기 (깊이 1단계)
- 부모당 파생 3개를 넘기기 — 그건 범위 설정이 틀렸다는 신호다

## 막혔을 때

멈추지 않는다. `deputy note <번호> "무엇에 어떻게 막혔는지"` 로 이슈에 남기고
`deputy next` 로 다음 할 일로 넘어간다. 사람이 폰으로 읽고 코멘트로 답한다.
