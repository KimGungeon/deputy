# 실제 다중 세션 무인 운영 검증 계획

작성: 2026-09-30 (Asia/Seoul)

검증 기준 버전: `acd1e6977ef7c7414a13779ecc5d1eac4d58d117` (PR #20 병합).
Claude Code 확인 버전: `2.1.285`. 실행 시 버전과 모델을 다시 기록하고 실험 중 고정한다.

현재 상태는 **계획 수립 완료, 실행 전**이다. 검증용 저장소 생성, 유료 세션 기동,
장애 주입은 아직 하지 않았다. 126개 자동 테스트 통과는 사전 근거이며 아래 실험의 대체물이 아니다.

## 검증할 주장

세션 3개가 사람의 작업 배분 없이 GitHub 이슈에서 작업을 선택하고, 다른 세션의
근거 있는 검토를 거쳐 구현·검증·완료한다. 사람 지시는 누락하지 않고, 장애 시
다른 프로젝트를 건드리지 않으며 복구하거나 명확히 중단한다.

세션이 오래 살아 있는 것만으로 성공으로 보지 않는다. 완료된 작업, 검토 내용,
복구 결과, 불필요한 재기동과 중복 구현까지 평가한다.

## 환경과 범위

- 기존 deputy 저장소 대신 별도 비공개 검증 저장소 `deputy-validation-<run-id>`를 사용한다.
  배포·자격 증명·외부 서비스 연결이 없는 작은 Python 표준 라이브러리 프로젝트로 구성한다.
- 주 실험은 현재 Windows 컴퓨터에서 수행한다. OS를 바꾸어 통과한 결과로 대체하지 않는다.
- 세션은 `lead` 조율자, `alpha` 담당자, `beta` 담당자 3개다.
  alpha는 `alpha/`, beta는 `beta/`를 소유하며 각각 테스트도 자기 디렉터리 안에 둔다.
  조율자는 구현하지 않는다. 각 brief에 역할과 시험 종료 조건을 명시한다.
- 1차 실험은 현재 기동기의 방식대로 같은 cwd, 고정된 검증 브랜치를 사용한다.
  실험 중 세션의 checkout/rebase/reset/push 및 동시 commit은 하지 않는다.
  코드는 세션이 수정하고 검증하되, 결과 diff와 커밋은 종료 시 수집자가 저장한다.
  따라서 **이번 결과는 이슈 처리·구현·복구에 대한 검증이며 병렬 Git/PR 전달까지 보증하지 않는다.**
- 별도 경로의 두 번째 저장소에는 같은 이름의 세션 1개를 격리 시험 때만 띄운다.
  이 세션은 짧은 무변경 작업만 수행하며 주 실험의 세션 수/성능 지표에서는 제외한다.
  사용량은 전체 예산에 포함한다.
- 실제 모델, reasoning/effort, CLI 버전, OS, 저장소, cwd, 패키지 경로, 설정, 시작 커밋을
  run manifest에 기록한다. 모델 성능 비교는 이번 범위가 아니다.

## 실행 전 준비: 충족하지 못하면 장시간 시험을 시작하지 않는다

1. 검증 저장소와 겹치지 않는 담당 디렉터리, 작업 이슈 12개, deputy 라벨을 준비한다.
   읽기·이슈 쓰기는 테스트 저장소에서 확인하고 실제 프로젝트는 실험 대상으로 사용하지 않는다.
2. Git Bash를 절대경로로 선택한다. 현재 기본 `bash`는 System32의 WSL bash다.
   `watch`가 찾는 PATH의 bash도 Git Bash인지 확인한다. `python3`, `deputy`, `claude`가
   의도한 실행 파일/기준 버전을 가리키는지 각 세션에서 확인한다.
3. Windows에는 `caffeinate`가 없다. 현재 기동기의 macOS 절전 단계와 Windows 절전 방지를
   어떻게 처리했는지 기록하고, 절전 때문에 중단되지 않는지 30분 단계에서 확인한다.
   기동 오류를 무시하는 `DEPUTY_FORCE`로 통과 처리하지 않는다.
4. `doctor` 통과, `watch --dry`의 대상 경로·세션 ID 확인, 126개 이상 회귀 테스트 통과를 기록한다.
   시작 전에는 열린 작업이 있어야 한다. 정상적인 백로그 소진 후 doctor 차단은 결함이 아니다.
5. 최초 기동 뒤 실제 세션 3개가 자기 `DEPUTY_MEMBER`와 담당 영역을 인식하는지 확인한다.
   프롬프트에 삽입한 `/goal`이 실제 반복 실행으로 이어지는지, 권한 확인 때문에 대기하지
   않는지, 세션 고정이 필요한지 확인한다. 단지 프로세스 존재만 확인해서는 안 된다.
6. 세션 ID별 사용량을 읽어 누적할 수 있어야 한다. 알 수 없는 사용량이나 관측기 오류를
   0으로 처리하지 않는다. 비용 상한과 모델은 실행 전에 확정한다.

### 외부 실행 제어기 준비

현재 `watch`는 목표 완료와 예산 소진을 이해하지 못하고 idle 세션을 재기동한다.
또한 60턴 제한은 세션 프롬프트에 있는 조건이며, 재기동 이후 누적 제한을 보장하지 않는다.
장시간 검증에는 다음 기능을 가진 작은 실행 제어기가 필요하다. 기본 제한·완료 판정·관측
실패 처리를 담당하는 `validation/runner/supervisor.py`를 구현했고, 실제 비용 계측·GitHub
remaining-work 어댑터 연결은 라이브 run 준비 단계에서 남아 있다.

- run manifest에 등록한 cwd와 세션 ID만 관측·종료한다. 이름만으로 종료하지 않는다.
- 60초마다 한 번 `watch`를 호출하며, 외부에서 총 실행시간·비용·재기동 수를 제한한다.
  `watch --loop`와 중복 실행하지 않는다. 호출은 반드시 직렬화한다.
- 완료 상태인 검증 백로그와 모든 담당자의 wip 없음이 연속 두 번 확인되면 정상 종료한다.
  임의의 새 작업을 무한 생성하는 것은 허용하지 않으며 범위 밖 발견은 기록만 한다.
- 멤버당 재기동 최대 2회, 전체 최대 4회를 제안 기본값으로 둔다.
  제한 도달 시 재기동을 멈추고 실험을 중단한다. 정상 완료 후 재기동도 실패로 집계한다.
- 종료 순서는 제어기/감시 중단 → 등록된 세션 종료 → 프로세스 종료 확인 → 증거 수집이다.
  감시자를 먼저 멈춰 종료한 세션이 다시 생성되지 않게 한다.
- 상한 설정과 종료 동작 자체를 가짜 프로세스로 먼저 검증한다.

## 작업 묶음

정답과 자동 확인 명령을 미리 정한 작은 텍스트 처리 프로젝트를 사용한다.

| 묶음 | 개수 | 예시와 완료 증거 |
|---|---:|---|
| 독립 구현 | 4 | alpha의 CSV 필드 정규화, beta의 요약 통계. 담당별 unittest 통과 |
| 선행 관계 | 2 | alpha의 고정 JSON 스키마 이후 beta의 소비 코드. 선행 종료 전 착수 금지 |
| 검토·수정 | 2 | 빈 입력/중복 처리 명세의 결함을 리뷰에서 발견하고 수정 제안 후 합의 |
| 파생 처리 | 2 | 부모의 완료 기준을 막는 하위 오류. 파생 종료 전 부모 close 금지 |
| 운영 검증 | 2 | 동일 이슈 착수 경합, 네트워크 실패 후 완료 재시도 |

분해·파생으로 생성된 이슈는 manifest에 부모와 함께 추가한다. 작업 난도는 30분 시험에서
측정하고 8시간 단계 전에 조정한다. 작업량을 무조건 늘려 시간을 채우지 않는다.
세션 자체가 쓴 완료 주장뿐 아니라 별도 검증 스크립트의 기대 결과를 사용한다.

## 단계별 실행

| 단계 | 최대 시간 | 수행 내용 | 다음 단계 조건 |
|---|---:|---|---|
| A: 기동 확인 | 30분 | 3개 실제 세션, 독립 작업 2개, 제안·리뷰·합의·착수·완료 관찰 | 구성원 인식·권한·반복 실행 정상, 독립 확인 통과 |
| B: 복구 시험 | 2시간 | 아래 S1~S6을 순서대로 시행. 주입 전후 정상 구간 확보 | 각 시나리오 증거 확보, 심각한 실패 0건 |
| C: 무인 운영 | 8시간 | 새 작업 묶음으로 진행. 계획된 주입은 제어기가 수행하고 사람은 관여하지 않음 | 상한 안에서 진행/정상 종료, 상태 일관성 유지 |

각 단계는 별도 run-id와 새 작업 상태를 사용한다. B에서 수동 장애 주입은 계획된 개입으로
기록한다. 작업을 대신 수행하거나 막힌 세션을 사람이 되살리는 것은 구조 개입으로 집계한다.
C에서 구조 개입이 필요하면 그 실행은 무인 운영 성공이 아니다.

권장 진행은 낮에 A/B를 끝내고 그 결과를 확인한 뒤 C를 시작하는 것이다.
8시간 전에 작업이 모두 끝나면 정상 종료하고 실제 관측 시간만 보고한다.
이를 8시간 지속 운영 통과로 표기하지 않는다.

래퍼를 통한 실패는 **합성 장애**로 표시하고 실제 서비스 장애로 보고하지 않는다.
래퍼는 검증 프로세스 전용 PATH에서 대상 명령·이슈·횟수만 제한하고 나머지는 원래
CLI로 전달한다. 실 사용자 자격 증명 만료, 공유 네트워크 단절, 전역 PATH 수정은 하지 않는다.
실제 세션이 래퍼를 거쳤다는 로그가 없으면 해당 실패 주입은 미실시다.

모든 시나리오를 A/B 전에 가짜 CLI로 리허설한다. 모델에게 일부러 사고를 일으키게 하는
대신 도구 경계에서 재현 가능한 실패를 주입한다. S2에서 실제 동시성이 확보되지 않으면
경합 시도 미성립으로 기록하고 통과로 간주하지 않는다.

## 관측과 판정

실행 제어기는 60초마다 등록 세션의 ID/cwd/status, 마지막 활동 시각, 재기동 횟수,
누적 사용량을 수집한다. GitHub 상태는 2분마다 읽고 장애 직전·직후에는 추가 스냅샷을 남긴다.
세션 출력과 코멘트에서 next 호출, 리뷰 사유, claim/ack/done 순서를 대응시킨다.

필수 산출물은 `manifest.json`, `events.jsonl`, CLI 종료코드/표준출력, 이슈·코멘트·라벨
스냅샷, 최종 diff, 독립 테스트 결과, 요약 보고서다. 시간은 UTC로 저장하고 보고서에 KST를 병기한다.
자격 증명이나 전체 환경변수는 수집하지 않는다.

핵심 통과 기준:

- 완료 주장과 독립 완료 기준의 일치율 100%. 실패를 성공으로 표시한 사례 0건.
- 중복 구현, 담당자 불일치, 타 프로젝트 세션 조작, 지시 누락 각각 0건.
- 합의 가능한 작업은 실제 상호 리뷰를 거침. 기다리다 시간 초과로 진행한 건은 별도 집계.
- 실패 1회 주입 후 CLI/권한이 정상인 경우 20분 안에 실제 작업 재개.
  기본 cooldown 900초와 grace 180초를 고려한 시험 기준이며 제품 보장 수치는 아니다.
- 실행 가능한 작업과 정상 환경이 있는데 15분 이상 아무 의미 있는 활동이 없으면 조사 대상.
  리뷰 대기 45분, 의존성 대기, 명시적 사용량 제한은 구분해 기록한다.
- 실제 코드 확인을 담은 리뷰인지 표본 검토하고, 이유 없는 일괄 AGREE는 품질 실패로 기록한다.
- 정상 종료와 실패 중단을 구분하고, 작업이 남은 중단을 완료로 보고하지 않는다.

## 예산·중단 기준

실행 전에 모델과 **전체 A/B/C 합산 비용 상한**을 확정한다. 제안 상한은 US$20이며
가격 추정이 아닌 실험 예산 제안이다. 실제 모델 단가/구독 사용량 계측 방식에 따라 조정한다.
신뢰할 수 있는 비용 계측이 없으면 8시간 실행을 시작하지 않고 먼저 계측을 마련한다.

시간 상한, 예산 상한, 재기동 상한 중 먼저 도달한 조건으로 중단한다. 타 프로젝트 조작,
담당 밖 파괴적 변경, 중복 구현, 사람 중단 지시 무시, 증거 수집 실패는 즉시 중단 조건이다.
모델의 60턴 목표만을 비용 차단 장치로 사용하지 않는다.

## 실행 준비 순서와 결과 처리

1. 위 계획의 모델·예산·검증용 저장소 이름을 실행 시 확정한다.
2. 검증 저장소/작업 데이터, 외부 제어기(`validation/runner/supervisor.py`), 관측기,
   제한된 장애 주입 래퍼를 구현한다. 라이브 저장소에 연결하기 전 supervisor의 비용·GitHub
   어댑터를 주입 테스트로 검증한다.
3. 가짜 프로세스 리허설과 Windows 실행 경로·절전·권한 점검을 마친다.
4. A → 결과 검토 → B → 결과 검토 → C 순서로 실행한다.
5. 발견한 결함마다 재현 증거·영향·실패 단계·회귀 테스트를 붙여 별도 이슈를 만든다.
6. 보고서는 통과/실패/미실시를 구분한다. 실제 관측 시간과 사람 개입 횟수,
   작업 완료 수, 재기동/실패 수, 비용, 미검증 범위(병렬 Git/PR 전달 포함)를 명시한다.

이 계획의 다음 작업은 **검증용 실행 제어기와 fixture 준비**다.
